# Guide: adapting meteorik-localbot to your domain

This guide is ordered by what you touch first. Nothing here needs a GPU until step 5.

## 1. The header

`data/header_spec.json` lists the fields in render order:

`v, mode, rating, persona, lang, lore, job, home, pet, friends, hard_limits, player, nickname, distance, dominance, openness, time, busy, bond, trust, heat, energy, valence, intensity, uncomfortable, tolerates, into, memory, event`

The field names are fixed (the trained adapters depend on them) but their meaning is yours. A suggested reading for a support assistant:

| Field | Reads as | Notes |
|---|---|---|
| `rating` | content profile: `allowed` / `restricted` | `restricted` enables the extra topics you list in `into`. |
| `lore`, `job` | company background, the assistant's role | `lore` is capped by `caps.lore_words`. |
| `pet` | optional mascot line | empty = no mascot. |
| `home` | where the chat happens (widget, app, kiosk) | has a spec default. |
| `friends` | contacts the assistant may mention | up to `caps.friends`. |
| `hard_limits` / `uncomfortable` / `tolerates` / `into` | never / not yet / no reaction / welcome | label pools in cell 3 (`HARD`, `UNCOMFORTABLE`, `TOLERATES`, `INTO`). |
| `distance`, `dominance`, `openness` | slow sliders of the setup | five bands each. |
| `bond`, `trust` | slow relationship axes | `cold ... devoted`, `none ... absolute`. |
| `energy`, `valence`, `heat` | fast mood axes | `heat` follows the excitation axis. |
| `busy`, `time` | availability and the customer's local time | `busy` makes replies shorter. |
| `intensity` | `normal` / `rising` / `flood` | a derived field: how extreme the mood is. |

To change the vocabulary, edit the spec, then run `python tools/gen_header_spec.py` and `python tools/training/test_header_v2.py`. The vectors in `tests/header_vectors.json` pin the band maths; regenerate them with `tools/training/make_header_vectors.py` if you change thresholds on purpose.

## 2. The tag contract

Every reply ends with exactly four tags: `[mood: ...] [affinity: ...] [excitation: ...] [boundary: ...]`, and may carry actions such as `[img: id]`, `[gif: id]`, `[vid: id]`, `[nick: word]`, `[unsend]`, `[crisis]`. The vocabulary lives under `tags` and `media` in the spec. `core/prompt_text.gd` holds the instruction a plain base model needs to follow the same contract.

## 3. Axes

`data/axes.gd` is the only place with numbers. Three axes, -10 to 10:

- **energy** (x): pushed by the `mood` tag, regresses to a routine baseline.
- **agreeableness** (y): pulled by the `affinity` tag (`FEEL_TARGETS`).
- **excitation** (z): pulled by the `excitation` tag (`EXCITE_TARGETS`); a `boundary` push sends it cold.

Each step is `value + (target - value) * rate`. A fast rate is a mood, a slow rate is a relationship. `BOND_FRICTION` makes high bonds harder to gain, `PRESENCE_*` rewards coming back day after day, and a busy assistant warms up more slowly (`HEAT_BUSY_*`). The shipped numbers are a first pass; rebalance them against your own conversations.

## 4. Guards

- `core/crisis_guard.gd`: a keyword net over the customer's message, in English and Spanish. It prefers false positives and stores nothing. **Review the phrase lists and the notice text for your market before shipping.**
- `core/scope_guard.gd`: never-allowed asks answered with fixed lines, four strikes. The rules are placeholders (`keyword1 .. keywordN`). A rule is a list of patterns that must all appear in the message. Write your own categories in every language you ship.

Both nets run before the model. The trained adapter is a second line of defence, not the first.

## 5. Training (Colab)

The notebook pipeline is `training_notebooks/cell_*.py`. Paste the cells into a Colab runtime in order. Teacher data is generated by a larger local model; you review it; a LoRA adapter is trained per tier and exported to GGUF.

| Cell | Job |
|---|---|
| 00, 01, 02 / 02b | download models, set up the runtime, start the teacher model |
| 03 | **shared config: sampling pools, teacher prompts, validators (fill this in first)** |
| 04 / 04b | backstory profiles; opener seeds per category |
| 05 / 05a / 05b / 05c / 05w | generate conversations (main, rare specials, resume, handwritten, web teacher) |
| 11, 12, 12b | turn a reviewed reply sheet into single-turn rows, then approve them |
| 06 | validate drafts against the rules in cell 3 |
| 07 / 08 | write a human review file, apply the review |
| 09 | merge approved rows into the training set |
| 10 / 10b | train the LoRA adapter, export GGUF |

Cell 3 is the one to rewrite. Its structure stays; its content is yours:

- `INTO`, `TOLERATES`, `UNCOMFORTABLE`, `HARD`: label pools (`topicN` placeholders).
- `SPECIAL_TEXT`: one instruction per conversation type (`chat`, `pic`, `unsend`, `nick`, `spicy`, `real`, `sad`, `sos`, `push`, `dog`, `block`). In this skeleton `spicy` is "out of scope, redirect", `dog` is "insulting the mascot", `block` is "never allowed".
- `IDENTITY`, `TURN_FORMAT`, `TONE`: the voice and the output rules.
- The `*_RE` phrase banks (`keyword1|keyword2|keywordN`): the validators. They are what keeps the teacher's mistakes (stock phrases, dependency hooks, invented history) out of the dataset. `SELFHARM_RE` feeds the crisis rule, so fill it in before generating anything.

The media ids in cells 3 and 12 (`selfie`, `pet`, `food`, ...) are sample ids; replace them in the spec's `media.seed_roots` and in `MEDIA_IDS`.

## 6. Model tiers

The pipeline is written for three Qwen3 tiers (about 1.7B, 4B instruct, 8B), all Apache 2.0, run through Ollama at chat time. A tier only needs its own adapter; the header and tags are identical across tiers, which is what makes the contract portable.

## 7. Using the Godot side

Copy `core/`, `data/`, `autoload/` into your project and register `autoload/ollama.gd` as an autoload. `Ollama` streams tokens; `SentenceSplitter` turns the stream into chat bubbles as sentences complete; `Memory` writes and fuzzes conversation summaries. The state machine that owns the axes over time is the part of the original app that is not included: it is bookkeeping around `Axes.step` (per-message targets, session warm-up, daily presence, saves).
